Act I

The Judgement Thesis

The frame everything else in this deck plays against

Skill Design for LLM Agents Watched Async

Minko Gechev - then you equip it

  • Prefer CLIs over MCPs: faster, use the user's own auth, no server to keep alive, easier to debug, better context preservation.
  • Write skills as deterministic procedure, not a conversation with a human.
  • Name and scope tightly - use negative triggers (e.g. an angular-testing skill that says "not for React or Vue") so agents don't reach for the wrong skill.
  • Keep the skill file lean; push detail into referenced resources so the model loads only what it needs.
Minko Gechev

Skills need evals too

  • Script repetitive sub-tasks and reference the script from the skill, rather than re-describing the steps.
  • For advanced cases, skills can nest and conditionally route to other skills.
  • Eval and test skills like you would code - catch regressions before they ship. "Skillgrade" builds and scores these tests.
  • Hill-climbing: a skill improving itself through automated self-evaluation over time.

The trap: "plausible code" - pipeline green, linter green, looks right, so why review it at all?

Sogl + Waardenburg

Deterministic guardrails, not prompted trust

  • A rules file (CLAUDE.md) is delivered as a user message - the agent can and will deviate from it once things get interesting. No compliance guarantee.
  • Put checks where they can't be skipped: hooks at specific lifecycle points, not blanket context. The agent takes the shortest path to "working" - so make the shortest path the correct one.
  • Tests are the spec: with TDD/BDD you own the spec, the agent owns the implementation. (Watch out - it's easy to let the agent write tests from the code, which just enshrines the bug.)
Sogl + Waardenburg

Who reviews the reviewer?

  • Same-model review shows family-level bias - GPT favours GPT, Claude favours Claude. Rubber-ducking, not reviewing.
  • Always use a different model to review than the one that wrote the code.
  • Two cheaper models reviewing each other gets close to one expensive model's review quality - for a fraction of the token spend.
Act III

Loop Engineering

What becomes possible once the guardrails are trusted

From Prompt Engineering to Loop Engineering Live in London

Valerii Latsko - the concept

  • Agents got fast; steering stayed manual - the human became the bottleneck. Loop engineering automates the steering: prompt → inspect → re-prompt → repeat.
  • The human keeps the goals, boundaries, and gates; the loop keeps the agent moving inside them.
  • Use cases: repo maintenance and triage, migrations and ports, small features, whole apps from a spec.
  • Proof it can run unattended for a long time: the "cursed" programming language ran on one evolving prompt.md for three straight months.
From One Repo to Hundreds Live in London

Konstantinos Leimonis - proof at scale

527 Repos migrated
87% No human in the loop
  • Started at 1 repo, 1 agent, 5 baseline steps - refined from there. Not manual, because scale demanded it.
  • Agents are stateless: read the board, write the result, stop. A deterministic contract tracks status and next steps, and the same loop resolves PR conflicts and pipeline failures.
Latsko + Leimonis

Tests are the agents' eyesight

Across both talks, the same load-bearing idea: autonomous agents need a deterministic signal of success to steer by. Tests are that signal - without them, "loop engineering" is just hoping at scale.

Verification matters more than autonomy. The goal was never removing the human - it was moving the human from steering every step to setting the goals and the checks.

Act IV

The Close

So what does this mean for how I work?

Debugging Performance With AI Live in London

Bernie Sumption - AI should make you better, not just faster

  • Rendering performance used to be a black box; a Chrome DevTools MCP server turns it into something you can explore and experiment with directly.
  • Always ask the AI what the options are, not just for the answer - that's how you build your own toolbox instead of outsourcing it.
  • AI is genuinely great at writing custom lint rules - a small, concrete way to turn a one-off fix into a standing guardrail.
Closing thought

Judgement, guarded by process

Every talk here pointed at the same thing from a different angle: pure coding ability matters less now, judgement matters more. That's true for the big calls (what's worth building) and the small ones (which model for which job, where to put a guardrail, when to trust an agent to run unattended).

The common thread I keep landing on is verification over autonomy - deterministic checks, the right model for the right stage, a different model reviewing than wrote it, tests as the signal an agent steers by. None of that is about slowing agents down. It's what makes trusting them further actually earned instead of assumed.

What I'm taking forward: keep building things and letting some of them fail, since that's still the only way I know to sharpen judgement. And keep asking AI what my options are, not just for the answer - that's the difference between it doing my job and it making me better at it.
